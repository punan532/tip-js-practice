## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Сначала весь синхронный код, затем микрозадачи в порядке постановки, затем таймер. |
| Фактический результат | A, B, C, D, E, F | Совпал с прогнозом. |

- Синхронный код: **A** (первая строка), **B** (тело async-функции до первого `await` выполняется сразу при вызове), **C** (последняя строка модуля).
- Микрозадачи: **D** — обработчик `Promise.resolve().then(...)`, поставлен в очередь раньше; **E** — продолжение после `await null`, поставлено при вызове `demonstrateAwait()` уже после D.
- **F**: `setTimeout(..., 0)` ставит задачу в очередь макрозадач (таймеров), которая обрабатывается только после того, как стек опустел и очередь микрозадач полностью выполнена, поэтому «0» не означает «немедленно».
- Если удалить обработчик D, порядок остальных меток не изменится: A, B, C, E, F.

Собственная добавка: перед строкой C в копию примера добавлен `Promise.resolve().then(() => log("G: собственный обработчик Promise"))`. Прогноз: A, B, C, D, E, G, F — G ставится в очередь микрозадач после E (E поставлено при вызове async-функции). Фактически: `A, B, C, D, E, G, F` — совпало.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API: маршруты задач и категорий, фильтры, ошибки в едином конверте, отладочные маршруты. Не изменялся. |
| `src/api-client.js` | Общий HTTP-клиент: `buildUrl`, `createApiClient` и `requestJson` (URL, заголовки, тайм-аут, отмена, проверка статуса и `Content-Type`, разбор JSON, `ApiError`). |
| `src/task-api.js` | Предметные операции: проверка фильтров до запроса, `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, проверка схемы ответа. |
| `src/variant.js` | Номер варианта и его фильтры: `variantNumber = 5`, `variantFilters = { categoryId: 1 }`. |
| `src/main.js` | Консольный сценарий: создание клиента, загрузка данных, вывод таблицы и контрольная ошибка 404. |

`fetchFn` передаётся в `createApiClient`, чтобы клиент можно было проверить без сети: модульные проверки подставляют функцию, которая возвращает заранее подготовленный `Response` или выбрасывает ошибку. HTTP-ошибки проверяются отдельно от сетевых, потому что `fetch` отклоняет Promise только при сетевой проблеме или отмене, а ответ 404/503 считается успешно полученным — без явной проверки `response.ok` ошибка сервера выглядела бы как данные. JSON после разбора проверяется по контракту (поля задачи, уникальность id, `meta.total`), потому что корректный синтаксис не гарантирует ожидаемую структуру.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; допускаются только `http:`/`https:` без query и hash; концевые `/` у базы и начальные у пути удаляются перед соединением. | Проверки 01, 04 |
| Кодирование query-параметров | `URLSearchParams.append` для каждого значения; `undefined`, `null`, `""` пропускаются, `false` и `0` сохраняются; входной объект не меняется. | Проверки 02, 03 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }` у каждого запроса. | Проверка 05 |
| Проверка `response.ok` | Сразу после получения `Response`, до проверки `Content-Type`; поля `code`, `message`, `details` берутся из `payload.error`, если тело — JSON. | Проверки 08, 09, 16 |
| Проверка `Content-Type` | Регулярное выражение для `application/json` и `application/*+json`; иначе `invalid-response`. | Проверка 10 |
| Разбор JSON | `response.text()` + `JSON.parse` в `try`; `SyntaxError` сохраняется в `cause`. Ответ 204 возвращает `null` без чтения тела. | Проверки 07, 11 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`; при срабатывании — `kind: "timeout"`. | Проверка 14 |
| Внешняя отмена | Внешний сигнал объединяется с тайм-аутом через `AbortSignal.any`; вид ошибки определяется по тому, какой сигнал сработал (`aborted` важнее `timeout`). | Проверка 15 |

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач: `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи: `[4, 13, 34]`, `meta.total = 3` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1 — Учёба`, `2 — Проект`, `3 — Организация` |
| `loadInitialData({ completed: false, priority: "high" })` | `{ tasks, categories, meta }`: 3 задачи, 3 категории, `meta` ответа задач |

Правила: задача — положительный безопасный целый `id` и `categoryId`, `title` строка 1–100 символов после `trim`, `completed` boolean, `priority` из трёх значений; категория — положительный `id` и непустое `name` до 100 символов. В коллекции `data` должен быть массив без повторяющихся id, а `meta.total` равен длине `data`. Любое нарушение — `ApiError` с `kind: "invalid-response"`. Фильтры (`completed`, `priority`, `categoryId`, `q`) проверяются до запроса; неизвестный или неверный фильтр — `TypeError` без обращения к сети.

## Последовательная и параллельная загрузка

Два запроса `/debug/delay?ms=300`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 605.5 | 605.6 | 605.4 | Время ≈ сумма задержек: второй запрос начинается только после первого. |
| `Promise.all` | 303.1 | 302.5 | 304.8 | Время ≈ самая долгая задержка: оба запроса стартуют сразу и ждут ответов одновременно. |

Ускорение объясняется тем, что запросы независимы и начинаются до общего `await`; при зависимых запросах или занятом сервере выигрыш был бы меньше.

## Вывод

Реализованы общий HTTP-клиент и предметный модуль задач; все три набора проверок проходят (18 + 26 + 13). Ожидание Promise само по себе не говорит об успехе: `await fetch` завершается и для ответа 404, поэтому клиент различает HTTP-ошибку (сервер ответил неуспешным статусом — `http` с `status`, `code`, `details`), сетевую ошибку (ответа нет вовсе — `network`), неверный ответ сервера (статус успешный, но не JSON или не та схема — `invalid-response`), тайм-аут (истекло собственное ограничение времени — `timeout`) и явную отмену (запрос отменил вызывающий код — `aborted`).
